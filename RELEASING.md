# Releasing the helper

This repository is downstream of `tcrn-workflow`. The order below is not a
preference; the values in step 2 do not exist until step 1 has happened.

Run `pnpm push-gate` before pushing. It re-derives every pinned digest from the
bytes it claims to pin, and it is the only thing that authorizes a push.

## 1. Workflow first

Cut the Workflow release and **tag it**. `IDENTITY` pins the commit, tree, and
annotated tag object, and none of those three ids is determined until the tag
object exists.

## 2. Re-pin `bootstrap/trusted-bootstrap.mjs`

```
IDENTITY.version     v<new version>
IDENTITY.commit      git rev-parse <tag>^{commit}
IDENTITY.tree        git rev-parse <tag>^{tree}
IDENTITY.tagObject   git rev-parse <tag>
```

## 3. Copy the provenance — do not write it

`manifests/complete-skill-archive.provenance.json` is a **byte copy** of the
Workflow repository's `dist/release/provenance.json`, which `verify:p8`
generates there. Copy it; never edit it by hand.

This is worth stating plainly because it has already gone wrong twice, in
opposite directions. Once it was hand-edited during a re-pin and kept an
`rc.5` source tar in its `subject` while claiming to describe `rc.6` — a
document asserting a build that nobody ran. Once a reviewer refused to touch it
at all, on the correct-sounding grounds that a SLSA in-toto statement must not
be fabricated. Both mistakes come from the same missing fact: **there is a
generator, and it lives in the other repository.** Neither writing it by hand
nor refusing to update it is right. Copying the generated bytes is.

The chain is: Workflow source tar → Workflow `release-manifest.json` →
`resolvedDependencies[0].sha256` in the provenance → `EXPECTED_PROVENANCE_SHA256`
here → the bootstrap's own bytes → the published anchor digest. Every link is
content-derived, so nothing in it is circular and nothing in it can be guessed.

Then re-derive:

```sh
shasum -a 256 manifests/complete-skill-archive.provenance.json   # EXPECTED_PROVENANCE_SHA256
shasum -a 256 artifacts/skill-archive.json                        # EXPECTED_ARCHIVE_SHA256
```

`EXPECTED_ARCHIVE_SHA256` only moves when something under `skill/` moves. If it
changed and nothing under `skill/` did, stop and find out why before continuing.

## 4. Republish the anchor digest — six documents

Steps 2 and 3 changed the bootstrap's bytes, so the SHA-256 a user checks by
hand is now different. Publish the new value in **all six**:

`README.md`, `README.zh-CN.md`, `README.ja.md`, `README.ko.md`, `README.fr.md`,
`SECURITY.md` — and in the GitHub release notes.

This is the step that gets missed, because it is the consequence of an edit
rather than the edit. A stale anchor in any one of these tells a reader that the
download was tampered with. `push-gate` fails on both a missing and a superseded
anchor for exactly this reason.

## 5. Rebuild the artifacts, in dependency order

```sh
pnpm archive                       # skill archive, source archive, SBOM
# rebind candidate-manifest.json: skillArchiveSha256, sourceArchiveSha256,
# and workflow.{version,commit,tree,tagObject}
rm -f artifacts/checksums.txt      # the generator publishes, it does not overwrite
pnpm checksums
pnpm verify
```

## 6. Run the whole suite. Not a subset.

Any commit touching `bootstrap/trusted-bootstrap.mjs`, `IDENTITY`, an
`EXPECTED_*` constant, or anything under `manifests/` **must** run `pnpm test`
in full before it is committed.

Artifact validation is not a substitute. A tagged commit once shipped with 22 of
72 tests red because `pnpm verify` was run in its place: `verify` checks that the
artifacts match their digests, and says nothing about whether the provenance
agrees with `IDENTITY`. The two answer different questions, and only one of them
was asked.
